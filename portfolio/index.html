왜 MVVM 기본 구조를 활용했나?
화면 표시와 입력·상태 처리의 역할을 나눠 다루는 기본 구조입니다. 기존 MVVM 기본 구조를 바탕으로 영상·분석 결과 표시, 분석·출력 자동화, 리포트 생성과 기관별 설정 등 주요 클라이언트 기능을 개발했습니다.
왜 Action과 Command로 나눴나?
Action은 전체 작업 흐름을, Command는 분석·출력 같은 내부 실행 단계를 구분하기 위한 구성입니다. Action Queue에서 순차 실행하고, 상태·완료·실패는 Qt Signal/Slot으로 전달해 실행 흐름과 상태 알림을 나눴습니다. 이 알림 구조를 Observer 관점에서 설명할 수 있습니다.

구조와 구현 이유

왜 파일별 Action과 내부 Command로 나눴나?
파일마다 로딩·분석·출력 단계가 이어지므로 파일을 하나의 Action으로, 내부 처리 단계를 Command로 구분했습니다. 실행 순서와 실패한 단계를 파일 단위로 다룰 수 있습니다.
왜 한 파일 실패 후에도 계속 실행했나?
한 파일의 오류로 나머지 파일까지 중단하지 않도록 실패 범위를 파일 단위로 나눴습니다. JSONL에 상태와 실패 메시지를 남겨 후속 확인·재처리할 대상을 구분했습니다.

입력·실행 설정
DICOM과 커스텀 프로젝트 파일(.mip)을 순차 분석하는 Macro를 개발했습니다. 파일·폴더 입력과 하위 폴더 탐색을 지원하고, 분석 프로젝트·Export 옵션을 JSON으로 저장·불러오도록 구성했습니다.

실패 격리
파일마다 독립 Action을 두고 내부 단계를 Command로 구성했습니다. 한 파일의 Command가 실패하면 해당 파일만 Failed로 기록하고 다음 파일의 Action을 계속 실행하도록 처리했습니다.
상태·로그 관리
NotStarted·Running·Success·Failed·Interrupted 상태와 실패 메시지를 JSONL로 남겼습니다. 진행 상태와 실패 메시지를 JSONL로 기록해 후속 확인에 사용하고, 전체 성공 시 해당 로그를 삭제하도록 했습니다.

왜 현장마다 화면과 제어 흐름이 달랐나?
장비 구성과 운영 순서, 실무자가 원하는 화면이 달랐기 때문입니다. 현장 요구를 확인해 AMX 통합제어 프로그램의 화면 디자인과 조작 흐름에 반영했습니다.
